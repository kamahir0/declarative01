# 宣言的なパズル設計の観察

以下はGitタグ`react-baseline`（`49805e3`）で保存した初期版の設計記録です。回転入力を1回ずつ再生する追加実験は[回転列の実験](rotation-queue.md)を参照してください。

## 正規状態と射影

ゲームの正規状態は、`pieces`、`holding`、`phase`の3つです。`useReducer`が保持し、純粋なReducerだけが更新します。パズル定義は状態の外に置き、ルール関数へ引数で渡します。標準の`gameReducer(state, action)`はサンプル定義に束縛した薄い関数です。異なる定義のテストには同じ`reduceGame`を使います。

完成状態、提出ボタンの有効状態、占有マス、論理的な回転方向、表示位置はすべて導出します。セル数も小さいため、キャッシュや同期用のEffectは設けていません。

Holding中の元の配置は`pieces`に残します。完成判定と進捗表示は確定した配置から計算し、描画と赤い重複マーカーはHoldingを優先した配置から計算します。完成した盤面から持ち上げても`isCompleted`はtrueのままで、`canSubmit`はfalseになります。この2つは異なる意味を持ちます。

Setで初めて配置・回転を確定します。Returnでは持ち上げ中の累積回転を保持してstockに戻します。次の選択もその回転から始めます。別ピースの選択、無効な移動、提出のフェーズ外通知はReducerが無視します。UIのdisabled属性とReducerの条件を併用するため、DOM以外からActionが届いても同じルールが適用されます。

## 回転を状態として持つ意味

`turns`は正負を許容した累積値です。論理形状は`((turns % 4) + 4) % 4`で決まり、表示角度は`turns * 90`で決まります。したがって、`-1`と`3`は同じ形状でも別の表示目標です。4回転後も0度へ値を巻き戻しません。

これはイベント履歴全体ではなく、操作に沿った回転経路を表す最小の情報です。論理上は不要でも、回転方向を保つ表示仕様には必要です。一方、同一描画フレーム内で「右→左」が入力されて合計が0に戻ると、途中の1回転は見えないことがあります。すべての入力を順番に見せる要件なら、別途キューや命令的なシーケンスが必要です。初期版は最新状態への遷移を優先します。

## 座標とアニメーション

論理座標はUnityと同じ左下原点です。右回転は`(x, y) → (y, -x)`とし、回転後の形状を左下へ正規化します。画面ではyを反転させます。サンプル解の座標と回転回数もUnityと共通です。

移動・回転はMotionの`animate`に現在の目標値を渡すだけです。新しいActionで目標が変わると、その目標へ遷移します。アニメーションの現在値をGameStateへ保存したり、完了を待って次の移動を許可したりはしません。[Motionの宣言的アニメーション](https://motion.dev/docs/react-animation)を利用しています。

形状の左下原点にそのままCSS回転を適用すると、回転後の占有マスと描画位置がずれます。Pieceは回転後の幅・高さから描画中心を導出し、外側のMotion要素でその中心へ移動し、内側で元の形状を累積角度だけ回転します。回転の中心と盤面原点を分けるのは表示の計算であり、GameStateの追加情報ではありません。

ブラウザテストは全9個、0から-4回転までの各方向について、描画された各セルの中心を盤面座標へ戻して`getOccupiedCells`と照合します。状態の数値だけを検証するテストでは、CSSの回転中心の問題は発見できません。

MotionConfigはユーザーのReduced Motion設定を尊重します。移動・回転の補間が無効でも、提出の発光と完了通知は機能します。

## 演出と時間的な処理

`playing → submitting → celebrating → finished`をGameStateで表現します。提出成功を受けた後、`celebrating`を各ピースのVariantsへ渡します。パズル定義の順序でA〜Iの発光開始を0.2秒ずつ遅らせ、各ピースは0.5秒かけて発光して戻ります。発光開始順は順次で、隣のピースの発光とは一部重なります。

最後のピースの`onAnimationComplete`だけが`CELEBRATION_FINISHED`をdispatchします。演出時間と同じ長さの別タイマーは設けません。コールバックが複数回届いてもReducerは`celebrating`以外では無視します。演出中の再提出やピース操作は許可しません。やり直しはセッションを再マウントし、Motion要素を破棄します。

発光順・時間・間隔が固定で、演出中の入力も不要な今回の仕様では、Variantsと遅延だけで記述できます。一時停止、途中からの再開、任意の時点からの逆再生、複雑な再実行は実装していません。これらを追加する際には、[Motionの命令的API](https://motion.dev/docs/react-use-animate)と比較する余地があります。今回の実装だけから命令的制御より優れているとは判断できません。

## 非同期処理と命令的な境界

SubmitのPromiseはReducerの外で実行し、結果だけをActionへ変換します。APIへ渡すのは`SUBMIT_STARTED`前のimmutableなスナップショットです。提出中の状態を`canSubmit`で再検証すると、phaseがsubmittingなので必ずfalseになるためです。

初期サービスは650ms後にローカルで完成条件を確認し、`{ accepted }`を返します。ネットワークやランダムな失敗はありません。エラーと受付拒否はテスト用サービスで再現します。`PuzzleGame`の`submit` propでサービスを差し替えられます。

ゲームの多重送信はphaseとReducerで防ぎ、Reactの次の描画より前に起きる連続入力はAbortControllerのrefで防ぎます。refは実行中の処理のハンドルです。ゲームの正規状態の写しではありません。アンマウント時にabortし、signalを無視して解決するサービスでも古い結果はdispatchしません。失敗時には`SUBMIT_FAILED`でplayingへ戻し、配置を維持します。

失敗の説明文はローカルのUI stateです。完成判定やゲーム操作を左右しないため、GameStateには含めていません。再提出・新しいセッションでリセットします。

キーボード購読もEffectで登録・解除します。Tabで移動したボタンのEnter・Spaceは標準のボタン操作として残し、マウス選択後はゲーム操作として扱います。この入力方式の違いをrefで追跡します。ゲームルールとは独立したUI入力の責務です。

初期版ではUseCaseクラスやRepository、アニメーションの汎用キャンセル管理層を作っていません。外部処理のハンドルとライフサイクルだけを素朴に命令的に記述しています。

## Unity版と比較して減ったもの・増えたもの

| 観点 | Unity版 | React版での観察 |
|---|---|---|
| 正規状態の保持 | RepositoryをUseCaseから更新 | useReducerに集約できる |
| 表示の反映 | Presenterの射影とViewへの反映 | Propsの再描画で反映できる |
| 移動補間 | Tween開始・置換とViewの連携 | animateの目標値の更新で扱える |
| 順次発光 | PresenterとDOTweenシーケンスの連携 | phaseとVariants、最後の完了通知で扱える |
| 回転方向 | QuarterTurnの4方向 | 累積値が必要になり、論理方向と表示角度が分かれる |
| 座標の反映 | Unityの左下原点で表示 | CSSの上原点への変換と回転中心の補正が必要 |
| 外部処理 | Gateway、キャンセル、Repositoryの照合 | Promise、ref、Effect cleanupが必要 |
| 入力 | Unityの入力イベント | DOMのフォーカス・標準ボタン操作との調整が必要 |

今回減ったのは、主に状態をViewへ同期する配線とTweenを開始し直す処理です。残ったのはパズルルール、非同期処理の競合、表示座標の計算です。増えたのは累積角度、Reactの描画前の入力競合への対処、DOMのフォーカス操作です。フレームワークが時間や入力の意味まで自動で解決するわけではありません。

## 今後の検証課題

初期版で観察できたのは、Stateからの表示導出、累積回転、連続入力の最新目標への追従、セッション破棄による中断です。今後は「すべての回転を順に再生」「演出の途中から再開」「演出だけを再実行」「盤面とstock間を連続的に移動」を同じ仕様で比較すると、宣言的制御と命令的制御の差をより具体的に検証できます。

stockと盤面は別の表示要素です。stockから持ち上げると盤面中央に現れ、Returnで盤面から消えます。この区間の共有要素アニメーションは導入していません。宣言的な表現を維持するためだけの仕組みを追加せず、要件が生じた時点で複雑さを評価します。

# 回転入力をすべて順番に表示する実験

## 保存したベースライン

初期React版はGitタグ`react-baseline`、コミット`49805e3`に保存しました。実験は`experiment/react-rotation-queue`ブランチで行います。初期版の設計記録は[architecture.md](architecture.md)です。

ベースラインの`animate={{ rotate: turns * 90 }}`は、新しい状態への追従を簡潔に表現します。しかし同じReactバッチ内で右→左を入力すると、途中の`turns = 1`が描画されず、0度のままになります。実装変更前に新しいブラウザテストを実行し、実際のDOM角度の最大値が0度だったことを確認しました。同じテストは追加実装で成功しています。

## 仕様と操作方針

右・左の各回転を0.2秒のlinear補間で再生します。回転中も左右回転の入力を受け付け、受理した回転は入力順にすべて再生します。論理状態は入力を受理した時点で更新され、表示はその列を後から追います。列が空になると、表示角度は論理上の累積回転数×90度に一致します。

Restartは既存のセッション再マウントを使用し、回転要素をアンマウントして現在の再生を中断します。未再生の列もセッションとともに破棄します。

回転途中でピースが消えたり、別の姿勢から再生を始めたりしないよう、移動・Set・Return・Submitは列の終了まで待ちます。待機中のキー操作はUIのボタンと同じく無効です。入力を予約して後で実行することはありません。回転とRestartは無効にしません。

この実験では各回転を必ず0.2秒表示するため、回転要素には`MotionConfig reducedMotion="never"`を指定しました。盤面上の移動補間は従来どおりユーザーのReduced Motion設定に従います。

## 宣言的APIの検討と採用

| 候補 | 今回の仕様に対する問題・判断 |
|---|---|
| 最新の累積角度を`animate`へ渡す | 入力途中の目標が上書きされ、相殺された回転列を復元できない |
| 列全体をkeyframesやVariantsへ渡す | 再生中の追加、完了済みの区間、再実行する範囲を別途扱う必要がある |
| 先頭1件の開始・終了角を宣言し、完了通知で先頭を取り除く | 現在の再生を変えずに後続を追加できる。今回の固定長回転に採用 |
| `useAnimate`で1件ずつ`await`する | 実現可能だが、ループの実行中フラグ、処理のハンドル、キャンセル後の継続判定が必要になる |

採用したのは`initial`、`animate`、Variants、`transition`、`onAnimationComplete`です。同じMotion要素を保持し、各回転のIDを`rotation-0`のようなVariantのラベルにします。先頭IDが変わると次の終了角へ遷移し、入力追加だけでは現在のID・目標が変わらないため、現在の回転は開始し直しません。完了通知のラベルが現在のIDと一致する場合だけ進めます。[Motionの宣言的な目標指定](https://motion.dev/docs/react-animation)と[完了通知](https://motion.dev/docs/react-motion-component)を利用しています。

完了通知で純粋なReducerにActionを送るという小さな橋渡しは必要ですが、追加の再生ループ、Effect、アニメーション制御用のrefは不要でした。今回の固定長・直列・Restartで全中断という仕様では、宣言的な方法が過度に複雑にならなかったため、[useAnimate](https://motion.dev/docs/react-use-animate)は採用していません。汎用タイムラインやアニメーションフレームワークも作っていません。

## 新しく必要になった状態と責務

GameStateとゲームルールのReducerはそのままです。`useReducer`が保持する外側の状態を次のようにしました。

```ts
type RotationPlaybackState = {
  game: GameState;
  rotations: readonly RotationStep[];
  nextRotationId: number;
};
type RotationStep = {
  id: number;
  from: HoldingState;
  to: HoldingState;
};
```

| 要素 | 必要になった責務 |
|---|---|
| `rotations` | 受理した回転の入力順と、各回転の開始・終了姿勢を未完了分だけ保存する |
| `rotations[0]` | 現在の再生対象。独立したactive状態としては保存しない |
| `nextRotationId` | 完了済みIDを再利用せず、遅れた完了通知と新しい回転を区別する |
| 表示用Reducer | 元のゲームReducerで入力の受理を判定し、受理したSPINだけを列に追加する。再生中の他操作を待たせる |
| Piece | 先頭の開始・終了角をMotionへ渡し、完了したIDを通知する |
| PuzzleSession | 正規状態と表示用の列を同じReducer更新で保持し、Restartで両方を破棄する |

`ROTATION_FINISHED`は表示用のActionです。先頭のIDと一致したときだけ取り除き、二重通知・古い通知・先頭以外の通知を無視します。完了通知でゲームの論理状態を更新することはありません。

既存のGameStateを保持するReducerと列を別々にdispatchする方法は採用しませんでした。回転の受理と列への追加を同じ純粋な更新で行うことで、Reactのバッチ化やStrictModeでも受理済みの回転を落とさずに済みます。

## 累積回転数だけでは不足する情報

`turns = 0`だけを見ても、「入力なし」「右→左」「右→右→左→左」を区別できません。最終角度からは、入力回数・符号の順序・どこまで再生済みかが失われています。方向は各Stepの`to.turns - from.turns`から導出するため、別のdelta状態は保存していません。

また、各回転時の位置補正も必要です。盤面上端の横長Hを右回転すると、縦長の形を収めるためyが5から2へ補正されます。続いて左へ回しても、yは2のままです。回転の累積値は0に戻りますが、最終値だけから最初の位置と途中の補正は復元できません。各Stepに原点と角度を含む姿勢を保存し、盤面上の描画中心も先頭Stepの終了姿勢から計算します。

再生中のピース表示と論理状態は意図的に異なります。完成判定・占有判定は従来どおり正規状態から計算します。未完了の列がある間は、表示途中の姿勢でSetやSubmitを確定できません。

## 解消できた複雑さと、新たに発生した複雑さ

宣言的APIが担当するのは、1件の角度補間、一定時間の再生、完了通知、アンマウント時の停止です。Tweenのハンドルを自分で保持して置換・停止したり、再生Promiseのキャンセルを管理したりする処理は追加していません。

一方、入力の時間的な意味はMotionだけでは表現できません。未完了の入力列、姿勢のスナップショット、完了IDの照合、論理状態と表示の遅れ、他操作をいつ許可するか、という責務が新しく必要になりました。特に完了通知による列の進行とVariantのラベルの照合はベースラインにはありません。回転ごとに要素を再マウントする方法も試しましたが、要素の準備を繰り返す必要があったため、同じ要素のVariant切替に整理しました。

列全体の再生をMotionに宣言するのではなく、「現在の1件を宣言し、その完了で次の状態へ進む」と分けることで、追加入力による現在の回転の上書きを避けられました。ただし、すべての入力を見せる仕様そのものに必要な履歴は、宣言的APIでも省略できません。

今回確認したUnityの追加実装は、複数ピースを跨ぐFIFO、Tweenの完了・Kill、待機Task、明示的なCancelを扱っています。Reactの今回の操作方針では、列が空になるまで持ち上げを保持するため、ピース跨ぎの再生は不要です。この操作方針の差もあるので、行数だけで宣言的APIと命令的APIの優劣は判断できません。

## 検証結果

Vitestは既存40件＋追加10件の**50件**、ChromiumのPlaywrightは既存8件＋追加7件の**15件**が成功しました。TypeScript検査とViteの本番ビルドも成功しています。

追加したブラウザテストでは、同一バッチの右→左、再生開始80ms後の追加入力、負の回転を含む12連続入力、各回転区間のDOM角度、壁際の最終セル、Restart直後の古いDOMの停止と新セッションの独立性、累積角度を保ったSet・再選択を検証します。テスト対象はReactのStrictModeが有効な実アプリです。

再生時間の設定は200msです。DOMのstyle変更を監視し、実際に動いている区間の角速度から90度の所要時間を算出します。フレームの計測揺らぎを考慮し、許容範囲は170〜235msです。各Stepが最後に表示した角度も次のIDへの切替時に検証します。観測した入力順・時刻・角度はテスト結果の`rotation-playback`添付JSONに保存します。

回転要素のマウントから次の状態のcommitまでの時間には、Motionの準備とReactの描画待ちも含まれるため、それをTweenの再生時間として測定しないようにしました。次の回転の開始には描画同期による待ちが入り得ます。ブラウザ停止・バックグラウンド化などを含む実時間の完全な保証や、回転間の待ちを必ずゼロにすることは対象外です。
